# 性能

[English](Performance)

### 预算

`copia-bench` 会在临时存储中写入 1,000 条卡片（其中 300 张图片），任何一项超出预算即失败。CI 在每次推送时运行它。

| 指标 | 预算 | 运行位置 |
|---|---|---|
| 空闲 CPU（卡片栏隐藏） | 60 秒平均 < 0.1% | CI 和本地 |
| 空闲内存（phys_footprint） | < 40 MB | CI 和本地 |
| 卡片栏打开时的内存 | < 120 MB | CI 和本地 |
| 从 ⌘Y 到第一帧（进程内） | 50 次打开的 p95 < 100 ms，卡片栏宽 1512 pt | CI 和本地 |
| 从 ⌘Y 到第一个呈现帧 | 50 次打开的 p95 < 100 ms | 本地，主显示器为 120 Hz 时才作为门槛 |
| 隐藏的卡片栏 | 没有视图 body 求值、图层绘制或 display link 回调，屏幕上没有窗口，卡片视图和缩略图已释放 | CI 和本地 |
| 滚动流畅度 | ≥ 95% 的帧在卡片行中显示新内容，且 ≥ 95% 的帧间隔 ≤ 1.5 × 刷新间隔 | 本地，主显示器为 120 Hz 时才作为门槛 |
| 动画收敛 | 打开、关闭、选中镜头、删除和撤销，开启与关闭“减弱动态效果”时都 ≤ 解析收敛时间 + 20 ms | 本地，主显示器为 120 Hz 时才作为门槛 |

默认参考宽度为 1512 pt，但不超过屏幕可用宽度；`--width` 可改变参考值，仍受屏幕宽度限制。面板左右各内缩 8 pt。比较结果前应查看 `stripWidthPoints` 和 `backingScale`：本地面板为 1496 pt，当前 CI 显示器得到的面板为 1008 pt、1× 缩放。只有主显示器为 120 Hz 或更高时，基于呈现帧的检查才作为门槛；在更慢的显示器上，它们照常测量，并连同刷新率列在 `reportedOnly` 中，因为 60 Hz 的一个刷新间隔（16.7 ms）几乎占满 20 ms 的收敛余量。冻结行对照和隐藏渲染对照在任何刷新率下都作为门槛。

### 两条路径

基准测试在启动时选择路径，并以 `path` 写入报告：

- **`screenCaptureKit`**：终端有屏幕录制权限（`CGPreflightScreenCaptureAccess()`）且没有传入 `--no-sck` 时运行。它录制基准测试自己的窗口，用于基于呈现帧的检查，然后同样运行进程内的 ⌘Y 测量。
- **`proxy`**：其他情况下运行。CI 可能走任一路径：当前 `xcode-27` 镜像授予了屏幕录制权限，应查看报告而不是假定运行代理路径。⌘Y 在进程内测量；需要录制的检查（滚动流畅度和所有动画收敛）会被跳过而不是判为失败。每个被跳过的检查及其原因都列在 JSON 的 `skipped` 中。

### 每项预算的测量方法

- **空闲 CPU 和内存。** 先打开并关闭一次预热，然后卡片栏在空闲窗口内保持隐藏。CPU 为 `getrusage` 时间除以墙钟时间，内存为 `phys_footprint`。打开时的内存在把选中项逐张移过每张卡片之后读取（每四张卡片暂停一帧，让卡片行滚动并创建每张卡片），此时还没有开始任何录制。
- **从 ⌘Y 到第一个呈现帧。** 从调用切换开始，到第一个捕获帧为止：该帧中第一张卡片的顶部（上方 16 pt，至少 8 pt 可见）与打开稳定后的帧一致。每次打开前都会选中第一条，因此第一张卡片位于行首。
- **从 ⌘Y 到第一帧（进程内）。** 从调用切换开始，直到面板在屏幕上且可见、卡片已挂载、行首卡片位置中有已提交内容的图层，并且又完成了一次事务。
- **隐藏的卡片栏。** `Diagnostics` 统计 SwiftUI 视图 body 求值（StripView 和 ClipCard）、面板计数根图层的 display 和 draw 调用，以及 display link 回调。Copia 没有自己的 display link，因此该计数按构造恒为 0。在空闲窗口内三项都必须为 0，且没有可见的 Copia 窗口。随后的正向对照会在卡片栏隐藏时强制重绘（修改一个卡片栏 body 读取的值、布局，并绘制根图层）。body 和图层计数都必须上升，否则基准测试失败。
- **滚动流畅度。** 由基准测试自己的 display link 以 4,000 pt/s 滚动卡片行 5 秒，约 90 张卡片，因此滚动期间会创建新的卡片和缩略图。每个呈现帧的卡片行都会计算哈希。哈希与上一帧不同即为新帧；窗口的起点和终点也计入帧间隔，因此任一端的卡顿都会被发现。以 0 pt/s 进行同样的滚动作为冻结行对照，它必须不通过该检查。
- **动画收敛。** 每种动画在强制关闭“减弱动态效果”时录制三次，强制开启时再录制三次。收敛时间从第一个有可见变化的帧之前一个刷新间隔开始，到此后动画始终保持在最终帧 1% 以内的第一帧为止；中位数必须 ≤ 解析收敛时间 + 20 ms。“1% 以内”按每种动画选用合适的度量：打开、删除和撤销跟踪移动内容离最终位置的距离占总位移的比例；选中镜头跟踪光环在两张卡片之间的位置；淡入淡出和交叉淡化跟踪与最终帧的亮度距离占本次试验最大距离的比例。解析时间来自 `Motion` 表：每条曲线最后一次偏离目标超过 1% 的时刻；删除则为完整淡出时长，加上完成回调启动的重排收敛时间。报告中还给出从 Animator 调用起测得的时间（`fromTriggerMs`），其中包含合成器上屏的延迟。相邻的文本条目有一到四句话，因此滑动一个位置的卡片不会与邻居的位置相匹配。

### 录制范围

- 只录制基准测试进程自己的窗口：`SCContentFilter` 由基准测试的面板和它的壁纸窗口构建，从不针对整块显示器，并且流被裁剪为面板的范围。
- 在整个录制期间，一个不透明、由基准测试拥有的渐变窗口位于面板正后方、低一级的窗口层级，因此玻璃只会采样这张壁纸。渐变只沿水平方向变化，所以垂直滑动仍是纯平移。
- 帧以 8 位亮度平面保存在内存中，滚动期间只保存哈希。不写入磁盘。
- 整个运行期间捕获保持暂停，因此从不读取系统剪贴板。录制时面板忽略鼠标，但打开时仍会成为键盘焦点窗口。录制期间点击其他应用会关闭卡片栏，并使那次试验无效。

### 结果

使用默认运行参数（空闲 60 秒、打开 50 次、动画 3 轮）测得，机器为 M3 Pro、macOS 27.2，release 构建，卡片栏宽 1496 pt（1512 pt 减去面板内边距），显示器为 60 Hz。两次录制运行和两次代理运行（`--no-sck`）的所有门槛检查都通过：

### 保持轻量的方法

- **只做轮询。** 空闲时唯一的工作是在一个有容差的计时器上每 0.5 秒读取一次 `changeCount`。
- **隐藏即释放内存。** 关闭卡片栏会丢弃卡片视图并清空缩略图缓存；窗口和宿主视图保留，因此下次打开很快。
- **小缩略图，在主线程之外解码。** 缩略图在后台任务中以 384 px 解码（足够 2× 显示器上 192 pt 的卡片），放入上限为 24 MB 的缓存。卡片从不保留自己的副本。
- **只有一层玻璃，使用系统阴影。** 卡片栏只有一层玻璃背景；窗口阴影由窗口服务器在 Copia 的内存之外绘制。
- **图片后面不用 `Canvas`。** 玻璃卡片栏中的 SwiftUI `Canvas` 棋盘格曾占用约 110 MB 的 GPU 缓冲区。现在改用 16 × 16 的平铺图片。

### 运行基准测试

```sh
swift build -c release --product copia-bench
"$(swift build -c release --show-bin-path)/copia-bench" --json bench.json
```

选项：`--idle SECONDS`（默认 60）、`--opens N`（默认 50）、`--width POINTS`（默认 1512）设置卡片栏宽度、`--no-sck` 即使有屏幕录制权限也运行代理路径、`--motion-rounds N`（默认 3）。运行期间捕获处于暂停状态，因此不会读取你复制的任何内容。

### 限制

- macOS 没有按进程的 GPU 时间计数器；“隐藏”通过渲染计数器和面板不在屏幕上来检查。
- 进程内的 ⌘Y 测量看不到实际呈现的帧。呈现时间还包括窗口服务器从提交到上屏的流水线（60 Hz 下约三个刷新间隔），以及滑入直到第一张卡片顶部可见的时间。
- 收敛时间按显示器刷新间隔量化（60 Hz 时为 16.7 ms），因此 20 ms 的余量只够大约一帧；这就是基于呈现帧的检查在 120 Hz 下才作为门槛的原因。
- 在 60 Hz 下，呈现的 ⌘Y 时间超过 100 ms，关闭、选中镜头和撤销晚一到两个刷新间隔收敛，约 5% 的滚动帧间隔偏长。作为门槛的 120 Hz 运行尚未进行：打开笔记本盖子，把内建显示器设为主显示器，然后运行基准测试。
- 有屏幕录制权限时才运行录制检查，否则报告会把它们列在 `skipped` 中。CI 镜像也可能授予录制权限。
- 删除在淡出的完成回调中启动重排。录制中的删除早于完整调度序列结束，原因尚未查明。预算按调度序列计算，不假定动画重叠。
